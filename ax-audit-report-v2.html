Convert ApiPaginatorV2.Builder runtime checks into compile-time types

Medium

What: ApiPaginatorV2.kt:159-171 throws 5 different RuntimeExceptions when required builder fields are missing. These are compile-time errors masquerading as runtime errors.

Before:

// libs/ApiPaginatorV2.kt:159-171
fun build(): ApiPaginatorV2<Data, Envelope, Params> {
    if (!::nextPage.isInitialized) throw RuntimeException("`nextPage` is required")
    if (!::envelopeToListOfData.isInitialized) throw RuntimeException("`envelopeToListOfData` is required")
    if (!::loadWithParams.isInitialized) throw RuntimeException("`loadWithParams` is required")
    if (!::loadWithPaginationPath.isInitialized) throw RuntimeException("`loadWithPaginationPath` is required")
    if (!::envelopeToMoreUrl.isInitialized) throw RuntimeException("`envelopeToMoreUrl` is required")
    return ApiPaginatorV2(...)
}

After: Use a staged-builder pattern so missing fields are a compile error:

interface NextPageStep   { fun envelopeToListOfData(f: ...): LoadWithParamsStep }
interface LoadWithParamsStep { fun loadWithParams(f: ...): LoadWithPathStep }
interface LoadWithPathStep   { fun loadWithPaginationPath(f: ...): MoreUrlStep }
interface MoreUrlStep        { fun envelopeToMoreUrl(f: ...): FinalStep }
interface FinalStep {
    fun startOverWith(o: Observable<Params>?): FinalStep
    fun build(): ApiPaginatorV2<Data, Envelope, Params>
}

Impact: Agents cannot produce a paginator missing a required field — the compiler refuses it. Eliminates 5 RuntimeException code paths.

suspend fun createBacking(input: CreateBackingInput): DomainResult<Checkout> {

suspend fun createBacking(input: CreateBackingInput): DomainResult<Checkout> =

                CreateBackingMutation(input.copy(clientMutationId = idempotencyKey.value))
            ).execute()
            ...
        } catch (e: ApolloException) {
            DomainResult.Failure(ProblemDetailsMapper.fromApollo(e))
        }
    }

FAIL

Why this matters: AI agents have limited context windows. Scattered features force agents to load multiple files and lose coherence. Self-contained modules let agents reason about one concept at a time.

We check for: Feature self-containment · Files under 300 lines · Colocated tests · Related types/constants live alongside implementation · shared/core contains only truly cross-cutting concerns

Pillar 1 · Severity: Critical · 160+ ViewModels in single directory
Issue: The viewmodels/ directory contains 160 files — one flat list for the entire app. Similarly, models/ (107 files), extensions/ (61 files), activities/ (46 files), and utils/ (35 files) are dumping grounds.

Tests are not colocated with feature code

Pillar 1 · Severity: High · 163 test files

Impact: Agents editing a feature must jump between app/src/main and app/src/test trees, losing coherence. Colocated tests are a core AX primitive.
Fix: As features migrate into features/<name>/, move their tests alongside. For Gradle compatibility, keep the src/test/java source set but place test files in a tests/ subdirectory within each feature module.

🔒 Pillar 2: Poka-Yoke & Contract-First Interfaces

NEEDS WORK

Why this matters: AI agents hallucinate when given loose types. any and untyped JSON invite the agent to guess the schema, leading to runtime errors. Strict contracts (sealed interfaces, domain primitives) force the agent to work within bounds.

We check for: Runtime boundary validation · No Any types or loose Record · Explicit return types · Discriminated unions via sealed classes · No public lateinit var

158 files use loose : Any types

Pillar 2 · Severity: Critical · 158 files
Issue: 158 files contain : Any, as Any, or Any? type references. Many are generic bounds (Envelope : Any in ApiPaginatorV2), but others are untyped payloads passed through transformers and mappers.
Impact: Agents cannot infer the shape of data at call sites. They hallucinate fields, invent properties, and produce code that compiles in their head but crashes at runtime.
Fix: Replace Any with sealed interfaces or concrete types. For the paginator, introduce a marker interface ApiEnvelope<T> with typed items: List<T> and moreUrl: String? accessors.

197 files use lateinit var — mutable uninitialized state

Pillar 2 · Severity: Critical · 197 files
Issue: 197 files declare lateinit var fields. These are runtime bombs: accessing before initialization throws KotlinUninitializedPropertyAccessException. Agents cannot statically determine whether a field is initialized at any given call site. Worst offender: KSApplication.kt:51-75 has 9 lateinit var fields for core services (cookieManager, pushNotifications, currentUser, ffClient, etc.).
Impact: Agents editing ViewModels will wire up calls in the wrong order, producing crashes that only surface at runtime. The type system is bypassed.
Fix: Migrate to constructor-injected val fields via Dagger/Hilt. For state that must change, wrap in a StateFlow<UiState> sealed interface. Keep lateinit var only for Android framework callbacks where it is unavoidable.

96 !! not-null assertions bypass the type system

Pillar 2 · Severity: Critical · 96 sites
Issue: 96 occurrences of !! across the codebase. Each one is a latent KotlinNullPointerException. Examples: SplashScreenViewModel.kt:595 (extras[APPLICATION_KEY]!! as KSApplication), KSApplication.kt:197 (t.cause as ApolloHttpException), CancelPledgeViewModel.kt:90 (as Project?).
Impact: Agents cannot predict when !! will throw. They cannot write retry logic around a KNullPointerException. Every !! is an unstructured error.
Fix: Replace with ?: return DomainResult.Failure(...) or as? T ?: .... The CancelPledgeBundleMapper shows the correct pattern.

Legacy models use @StringDef instead of sealed enums

Pillar 2 · Severity: High · e.g. models/Project.kt:64
Issue: Project.kt uses @State private val state: String with a @StringDef annotation. The compiler cannot enforce exhaustiveness — agents must guess valid states by grepping for constants.
Impact: Agents invent invalid state strings (e.g. "paused" when only "live", "successful", "failed", "canceled", "suspended" are valid). when blocks cannot be exhaustive.
Fix: Replace @StringDef with a sealed interface ProjectState and data object Live : ProjectState variants. Agents get compile-time exhaustiveness and auto-complete.

FAIL

Why this matters: AI agents rely on schema documentation to understand field semantics. Without explicit KDoc, the agent guesses — often incorrectly. Negative constraints ("Do not use for X") prevent misuse.

We check for: KDoc on public APIs · Format specifications (UUID, ISO 8601) · Negative constraints · Enum value documentation

Only 2.8% of declarations have KDoc

Pillar 3 · Severity: Critical · 260 KDoc blocks / 9,419 declarations

⚠️ Pillar 4: In-Band Actionable Errors (RFC 9457)

NEEDS WORK

Why this matters: When an AI agent hits an error, vague messages like "Invalid input" force it to retry blindly. Structured errors with suggested_action tell the agent exactly how to recover, enabling autonomous retry logic.

We check for: Structured error types · suggested_action field · is_retriable flag · RFC 9457 Problem Details format

SplashScreenViewModel.kt:199 — bare throw Exception()

Pillar 4 · Severity: Critical · viewmodels/SplashScreenViewModel.kt:199
Issue: A bare throw Exception() with no message, no type, no detail. The catch block on line 201 immediately admits: "todo: we're bringing the user into the app anyways to emulate current behavior". This is the worst kind of error — it tells the agent nothing.
Impact: Agents cannot determine what failed, whether to retry, or what action to take. The error is silently swallowed, hiding a real initialization failure.
Fix: Replace with DomainResult.Failure(ProblemDetails(TYPE_SERVER, "Feature-Flag Initialization Failed", ...)). See Quick Win #1 for the full before/after.

ApiPaginatorV2.kt — 5 RuntimeExceptions for builder validation

Pillar 4 · Severity: High · libs/ApiPaginatorV2.kt:159-171, libs/loadmore/ApolloPaginateV2.kt:147-153

Impact: Agents catch RuntimeException and have no idea whether to retry (no — it's a programmer error) or give up.
Fix: Use a staged-builder pattern so missing fields are a compile error. See Quick Win #3.

Apollo errors are not normalized to ProblemDetails

🛡️ Pillar 5: Machine-Tempo Safety & Idempotency

NEEDS WORK

Why this matters: AI agents may retry operations or run at high speed. Without idempotency keys, a retry could create duplicate resources. Without rate-limit hints, agents can overwhelm the system.

We check for: Idempotency-Key on mutating ops · Rate-limit headers · Retry-After backoff · Optimistic locking (ETag, version fields)

Only 6 files implement idempotency — critical mutations unprotected

Pillar 5 · Severity: Critical · 6 of 1,099 files
Issue: The new IdempotencyGuard and IdempotencyKey exist in ax/safety/, and are used in CancelPledgeContracts.kt and ApolloCancelPledgeRepository.kt. But the most dangerous mutations — CreateBackingMutation (create a pledge), CompleteOnSessionCheckoutMutation (charge a card), UpdateBackingMutation (change payment), CreatePaymentIntentMutation — have no idempotency protection.
Impact: An agent that retries a failed CreateBacking call creates duplicate pledges. An agent that retries CompleteOnSessionCheckout charges the user twice. This is a production-severity financial bug waiting to happen.
Fix: Every mutating Apollo call in KSApolloClientV2.kt must accept an IdempotencyKey parameter. The repository layer generates one per logical operation and passes it through. Replays return cached results. See Quick Win #4.

No rate-limit headers surfaced to callers

Pillar 5 · Severity: High · 3 files mention rate-limiting
Issue: Only 3 files reference rate-limiting concepts. KSApplication.kt:197-200 checks for HTTP 429 but only for logging. No OkHttp/Apollo interceptor surfaces X-RateLimit-Limit, X-RateLimit-Remaining, or Retry-After headers into the domain layer — even though RateLimitBackoff.fromHeaders() already exists in ax/types/DomainPrimitives.kt:160 and is ready to use.
Impact: Agents operating at machine tempo (e.g. batch-updating 100 backings) have no signal to back off. They hit 429s, retry immediately, and get throttled further — a thundering herd.
Fix: Add an OkHttp.Interceptor that reads rate-limit headers, parses them via RateLimitBackoff.fromHeaders(), and exposes them via a RateLimitState flow. Inject this into repositories so they can suspend before hitting the limit.

No optimistic locking for concurrent updates

Pillar 5 · Severity: Medium
Issue: Models like Backing, Project, and User have no version field or ETag support. Concurrent updates (e.g. two agents updating the same backing's reward selection) can silently overwrite each other.
Impact: Lost updates in multi-agent scenarios. The last writer wins with no conflict detection.
Fix: Add a version: Int field to mutable models. Require it in update mutations. Server rejects stale versions with a 409 Conflict mapped to ProblemDetails with isRetriable = true and suggestedAction = "Reload the resource and reapply your change.". Note: TYPE_CONFLICT is already defined in ProblemDetails.kt:68.

IdempotencyGuard framework is production-ready

The new ax/safety/IdempotencyGuard.kt provides a complete idempotency primitive with:

  • IdempotencyKey — validated value class with generate() and create() factory methods
  • runSingleFlight() — suspending wrapper that rejects overlapping calls with TYPE_IN_FLIGHT
  • Automatic Retry-After cooldown tracking via blockedUntilMillis
  • Testable clock injection via clockMillis: () -> Long
// ax/safety/IdempotencyGuard.kt:81-84
